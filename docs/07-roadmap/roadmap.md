# Personal Assistant 产品进一步开发规划

## 1. 产品定位

当前产品不应继续以“通用个人 AI 助手”作为第一心智切入。这个表述过宽，会直接进入 ChatGPT、Siri、Notion AI、各类手机系统助手的竞争场。

建议收敛为：

> 本地优先的 AI 记忆收件箱，帮助用户把微信群通知、截图、语音备忘、网页片段等碎片信息，一键变成可搜索、可提醒、可追溯的私人记忆库。

核心用户不是所有人，而是：

- 学生：课程群通知、作业、考试、报名、讲座、临时安排极多。
- 独立开发者/极客：愿意自托管，重视隐私和 BYOK，有大量技术资料和临时想法。
- 高信息密度用户：每天需要从聊天、截图、语音、网页里捞任务和事实。

## 2. 北极星指标

第一阶段北极星指标：

> 每周被成功找回或提醒的有效记忆数。

辅助指标：

- D1 留存：用户第二天是否继续录入。
- 每日捕获次数：用户是否把它当作默认信息入口。
- 解析确认率：AI 提取出的时间、任务、标签是否被用户接受。
- 回答可追溯率：问答是否能给出原始来源。
- 提醒命中率：提醒是否准时、准确、有用。

## 3. 产品原则

1. 捕获优先，聊天其次  
   用户每天最常发生的是“先存下来”，不是“开始一场 AI 对话”。

2. 准确优先，炫酷其次  
   时间、地点、任务、考试、作业这类事实信息必须可确认、可修正、可追溯。

3. 少配置，强默认  
   多模型、多 Provider、多端同步都是高级能力。默认体验必须能让用户 5 分钟内跑通。

4. 本地可信  
   产品的长期差异化来自本地存储、BYOK、私有部署、端到端加密，而不是模型能力本身。

5. 可解释的自动化  
   AI 可以自动提取任务，但必须让用户知道“它提取了什么、为什么这样提取、是否已启用提醒”。

## 4. 当前产品判断

已有能力：

- Go 后端、Flutter 客户端。
- SQLite 结构化存储与 Qdrant 向量存储。
- 文本、图片、语音入库。
- OCR、STT、TTS、多模型 BYOK。
- 语义检索、任务提醒、Dashboard、脑图、Telegram Bot、语音舱。
- E2EE 同步雏形。

主要短板：

- 首次配置复杂，普通用户难以上手。
- 核心使用闭环不够聚焦。
- AI 异步解析状态不可见，用户缺少确定感。
- 隐私承诺与部分实现不一致，例如 API Key 持久化、WebSocket query 传递密钥。
- 功能点过多，但没有一个被打磨到“每天必用”。

## 5. 阶段路线图

### Phase 0：产品收敛与可信基础

周期：1 周

目标：明确产品主线，冻结非核心功能扩张。

要做：

- 将产品主入口定义为“记忆收件箱”，而不是 Dashboard 或聊天。
- 梳理现有功能，分为核心、实验、高级三类。
- 暂停新增脑图、语音舱视觉特效、复杂 Agent 能力。
- 明确隐私边界：哪些数据留本地，哪些会发给模型，哪些会加密。

交付物：

- 新版 README 或产品介绍。
- 设置页的信息架构草案。
- 核心用户路径图。

验收标准：

- 新用户能在 30 秒内理解产品解决什么问题。
- 团队后续开发都围绕“捕获 -> 解析 -> 确认 -> 提醒 -> 回查”。

### Phase 1：打穿最小高频闭环

周期：2-3 周

目标：让用户愿意每天把碎片信息投进来。

核心路径：

1. 用户从 App、分享菜单、剪贴板、Telegram 或语音录入信息。
2. 系统立即生成一条记忆卡片。
3. 后台解析标题、时间、任务、标签、来源。
4. 用户看到解析结果，并能一键确认或修改。
5. 用户用自然语言找回信息，答案带来源。

功能优先级：

- P0：记忆卡片解析状态
  - 状态包括：待解析、解析中、已解析、解析失败、需确认。
  - 卡片上显示来源、原文、标题、标签、时间、任务。

- P0：解析确认卡片
  - 对时间、任务、提醒、优先级提供编辑入口。
  - 未确认的高风险提醒不自动触发，避免误提醒。

- P0：来源证据
  - 问答结果必须引用原始记忆卡片。
  - 对时间类问题，优先返回结构化数据，再补充语义上下文。

- P1：极速录入首页
  - 首页第一屏聚焦录入框、最近记忆、待确认事项。
  - Dashboard 指标下沉，不作为第一入口。

- P1：失败可恢复
  - OCR/STT/Embedding/LLM 失败时，原始内容仍必须保存。
  - 用户可手动重试解析。

验收标准：

- 从复制一段群通知到生成待确认提醒，流程少于 20 秒。
- 用户能清楚知道每条记忆是否已完成解析。
- 回答“下周有什么要交？”能返回任务、时间和来源原文。

### Phase 2：降低上手门槛

周期：2 周

目标：让非开发者也能成功跑通。

要做：

- 新手引导：
  - 第一步：连接后端。
  - 第二步：选择模式，云模型或本地模型。
  - 第三步：保存一条测试记忆。
  - 第四步：问一个测试问题。

- 推荐配置：
  - 默认只展示一套 Chat、Vision、Embedding、STT 推荐配置。
  - 高级多模型配置折叠到“高级设置”。

- 连接自检：
  - 后端健康检查。
  - SQLite 可写检查。
  - Qdrant 可连接检查。
  - 模型 API 可用检查。
  - STT/OCR 可选检查。

- 一键诊断报告：
  - 显示失败原因和修复建议。
  - 允许复制诊断信息。

验收标准：

- 新用户 5 分钟内完成首次录入和首次检索。
- 配置失败时，用户知道卡在哪里。
- 不懂 Qdrant/Ollama 的用户也能使用云模型模式。

### Phase 3：提醒与任务场景产品化

周期：2-3 周

目标：让产品从“能记住”升级为“真的帮我别忘事”。

要做：

- 待办中心：
  - 今日待办。
  - 未来 7 天。
  - 待确认提醒。
  - 已完成。

- 提醒确认机制：
  - AI 提取的提醒默认进入“待确认”。
  - 用户确认后才进入调度。
  - 低风险普通待办可自动保存，但不主动推送。

- 时间解析增强：
  - 支持中文相对时间：明天、下周一、这周五、月底。
  - 所有相对时间必须保存解析基准日期。
  - UI 展示原文时间和解析后时间。

- 推送策略：
  - Telegram/Bark 作为第一阶段推送。
  - 后续再考虑系统通知。

验收标准：

- 用户可以信任“今天/明天/下周”的待办列表。
- 每个提醒都能追溯到原始输入。
- 错误提醒可以快速删除或修正。

### Phase 4：隐私与安全重构

周期：2 周

目标：让“本地优先、隐私可信”成为真正卖点。

要做：

- API Key 安全：
  - 不再通过 URL query 传递 API Key。
  - WebSocket 鉴权与模型配置改为 Header 或短期会话令牌。
  - 本地持久化密钥需要加密或明确告知用户。

- E2EE 边界重构：
  - 加密记忆不应被后端明文解析。
  - 若用户希望 AI 解析加密内容，必须在客户端解密后显式发送。
  - UI 中说明“加密后无法被服务器侧 AI 自动索引”的取舍。

- 隐私说明页：
  - 数据存在哪里。
  - 什么会发给模型服务商。
  - 如何删除数据。
  - 如何导出数据。

- 数据导出：
  - Markdown/JSON 导出。
  - SQLite 备份说明。

验收标准：

- 产品承诺与技术实现一致。
- 用户能一键查看和导出自己的数据。
- 不再出现敏感 Key 进入 URL 的情况。

### Phase 5：垂直场景验证

周期：3-4 周

目标：从个人工具走向可验证的小市场。

建议优先验证“学生场景”：

- 微信/Telegram 群通知转任务。
- 截图 OCR 成课程/作业/考试提醒。
- 语音备忘转待办。
- “这周我有什么作业？”“下次考试在哪？”这类高频问答。

要做：

- 设计 10 个真实学生任务样例。
- 建立评测集：
  - 通知类文本。
  - 课程表截图。
  - 作业截图。
  - 语音备忘。
  - 模糊时间描述。

- 邀请 5-10 个真实用户试用。
- 收集：
  - 首次上手耗时。
  - 每日录入次数。
  - 解析错误类型。
  - 提醒是否有用。
  - 用户是否愿意继续用。

验收标准：

- 5 个用户中至少 3 个连续使用 7 天。
- 每人每周至少录入 15 条记忆。
- 时间/任务解析准确率达到 85% 以上。
- 用户能说出一个明确的“它帮我避免忘事”的案例。

## 6. 功能分层

### 核心功能

- 文本、图片、语音极速捕获。
- 记忆卡片。
- 解析状态。
- 任务/提醒提取。
- 用户确认与修正。
- 自然语言回查。
- 来源引用。
- 本地存储。

### 高级功能

- 多模型 BYOK。
- 本地 Ollama。
- Telegram Bot。
- Bark 推送。
- E2EE 同步。
- 数据导出。

### 实验功能

- 脑图。
- 语音舱。
- 用户画像。
- GraphRAG 实体关系。
- 自动执行复杂 Agent 任务。

实验功能不是删除，而是暂时不作为主卖点。

### P2

## 8. 不建议近期投入

- 复杂插件市场。
- 多用户 SaaS。
- 团队协作。
- 大规模权限系统。
- 过早做官网营销页。
- 过度优化脑图视觉。
- 复杂 Agent 自动执行。

原因：这些都会稀释当前最重要的验证目标，即用户是否愿意每天把碎片信息交给这个产品。

## 9. 产品成功标准

阶段性成功不是功能数量，而是用户行为变化。

好的信号：

- 用户开始把临时信息默认发给它。
- 用户主动用它查“之前那条通知”。
- 用户相信它的提醒。
- 用户愿意配置自己的 API Key 或本地模型。
- 用户愿意把数据留在里面超过一周。

坏的信号：

- 用户只把它当聊天机器人。
- 用户录入后不再回来。
- 用户经常不知道 AI 是否处理完成。
- 用户不信任提醒时间。
- 用户觉得配置比价值更重。

## 10. 一句话战略

未来 6-8 周，不追求“更像一个全能 AI 助手”，而是追求：

> 让用户把每天的碎片信息放心扔进来，并在关键时刻准确找回来。

这是最小、最硬、也最有商业潜力的产品路径。

## 11. 开发进度

### 2026-06-27：Phase 1 第一批

已完成：

- Memory 增加 `pending`、`processing`、`completed`、`failed` 解析状态。
- SQLite 自动兼容旧数据库，旧记忆默认标记为已解析。
- OCR、结构化提取和结果保存失败时记录可读错误原因。
- 原文先落库再调用 AI，模型配置或服务失败不再导致信息丢失。
- 增加 `POST /api/memories/retry?id=...` 手动重试接口。
- 同一条记忆限制为单个后台解析任务，避免重复并发处理。
- Flutter 卡片展示待解析、解析中和失败状态。
- 失败卡片支持一键重试，处理中条目自动轻量刷新。

下一批：

- 记忆详情页完整展示来源、原文、解析时间与失败原因。
- 问答结果增加可点击的原始记忆引用。
- 将任务确认区进一步收敛为首页“收件箱”主视图。

### 2026-06-27：Phase 1 第二批

已完成：

- Memory 增加 `needs_confirmation` 状态。
- AI 提取任务通过 `memory_id` 关联原始记忆。
- 保存模型返回的原始时间表达与来源原文。
- 新任务默认进入 `pending_confirmation`，不会被调度器执行。
- 增加任务确认接口，确认时可修正标题、备注、类型和时间。
- 用户确认后任务才进入 `pending` 调度状态。
- 忽略待确认任务不会删除原始记忆。
- 最后一条任务被确认或忽略后，父记忆自动变为已完成。
- Dashboard 增加待确认提醒卡片、来源证据、编辑与确认操作。
- 后台解析完成时自动刷新任务统计，无需用户手动刷新页面。

下一批：

- 首页重构为以录入和待确认为核心的“记忆收件箱”。
- 增加按来源类型和处理状态筛选。
- 为聊天历史持久化引用关系。

### 2026-06-27：Phase 1 第三批

已完成：

- Memory 新增不可变 `original_content`，与 AI/OCR 解析内容分离。
- 旧数据库自动使用现有内容回填原始内容。
- 图片详情直接展示原始图片，不再把 Base64 当作正文。
- 记忆详情完整展示来源类型、来源信息、录入时间、最近处理时间、处理状态和错误原因。
- 问答上下文增加稳定引用编号，提示模型在事实句后标注 `[1]` 等来源。
- 问答 API 返回结构化来源摘要，同时保持 `answer` 字段向后兼容。
- Flutter 聊天气泡展示可点击的来源记忆卡片。
- 点击引用时按 ID 加载完整记忆，并展示原始内容与解析内容。
- 图片防重复逻辑同时检查不可变原始内容。
- E2EE 流程同步加密、解密 `original_content`。

下一批：

- 首页重构为以录入、最近记忆和待确认为核心的“记忆收件箱”。
- 增加记忆来源类型、处理状态筛选。
- 将问答引用关系持久化到聊天历史。
